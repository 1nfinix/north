# 系统化排错

## 何时使用

出现失败测试、异常日志、性能退化或用户可复现的错误，且原因尚未确认时使用。先保护现场；涉及生产数据或敏感日志时只收集任务必要的脱敏信息。

## 分步流程

1. 写下预期结果、实际结果、首次出现的版本、平台及最短复现步骤。区分稳定失败和偶发失败。
2. 在 PowerShell 或 Git Bash 中可先运行以下通用命令；测试命令以项目现有脚本为准：

   ```text
   git status --short
   git log -5 --oneline
   git diff --check
   ```

3. 原样运行最小复现，记录完整命令、退出码和关键错误行。若只在某平台发生，记录该平台版本和配置变量名，不复制凭据值。
4. 从报错点沿调用链向输入追溯；每次只改变一个条件。用 `git grep -n 'errorText'` 或 `git grep -n 'functionName'` 找入口与处理点。
5. 提出可证伪的根因假设，设计能区分候选原因的最小实验。确认根因后在产生错误的地方修复，而不是隐藏异常或增加无依据重试。
6. 先运行复现测试，再运行相邻测试和相关静态检查。若改动涉及持久化、并发或权限，额外检查相应失败路径。
7. 总结根因、修复、验证范围和仍未验证的环境，不把“本机通过”推广为全平台通过。

## 检查清单

- [ ] 预期、实际和复现条件分别记录。
- [ ] 确认失败发生在当前代码或明确的版本上。
- [ ] 日志中的秘密和个人数据已在报告中脱敏。
- [ ] 实验一次只改变一个有解释力的变量。
- [ ] 根因假设能解释全部已知现象，包括失败条件。
- [ ] 修复不吞掉错误、不弱化安全或测试门禁。
- [ ] 回归包含原失败用例及至少一个相邻正常路径。
- [ ] 未能复现时保留证据与下一次需采集的信号。

## 输出格式

```markdown
## 现象
- 预期：
- 实际：
- 复现：`命令` → 退出码与关键输出

## 根因与修复
- 根因：证据链
- 修改：文件与行为

## 回归
- `命令` → 结果
- 未验证：环境与原因
```

## 常见陷阱

- 从第一条错误信息直接猜根因，忽略更早的失败。
- 通过延长等待、吞异常或跳过测试让症状消失。
- 同时改多个条件，无法知道哪一个起作用。
