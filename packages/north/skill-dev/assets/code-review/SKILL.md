# 代码评审

## 何时使用

收到待合并的变更、补丁或指定文件，且需要判断行为风险时使用。先确认目标分支、预期行为和审查范围；没有基线时请用户指定，不猜测比较对象。

## 分步流程

1. 读取仓库规则、变更说明和相关接口的使用方。检查工作区状态，避免把未提交的其他改动算入本次评审。
2. 在 PowerShell 或 Git Bash 中运行以下命令；将 `BASE` 换成实际基线分支或提交，不要直接复制占位符执行：

   ```text
   git status --short
   git diff --name-status BASE...HEAD
   git diff --check BASE...HEAD
   git diff BASE...HEAD -- path/to/file
   ```

3. 对每条变更沿输入、状态、输出、错误和清理路径追踪；同时查找调用者与持久化或外部接口。用 `git grep -n 'symbolName'` 查使用位置。
4. 核对已有测试是否覆盖预期行为和失败路径。按项目文档运行最小相关测试，记录命令、退出码与失败细节；不要把未运行的测试写成通过。
5. 对每个疑似问题构造具体触发条件。能用局部测试或静态证据确认就确认；无法确认的标为风险，不写成既定缺陷。
6. 按严重程度排序：阻断、严重、一般、建议。优先报告会改变结果、安全性或数据的事项，给出最小修复方向。

## 检查清单

- [ ] 变更范围和基线明确，未混入无关工作区改动。
- [ ] 新旧行为与调用方的期待一致。
- [ ] 空值、边界值、重复调用和错误返回有明确处理。
- [ ] 用户输入、路径、命令、SQL 与权限检查处没有注入或越权路径。
- [ ] 资源、锁、订阅和后台任务在失败与取消时释放。
- [ ] 循环、查询和网络调用没有随输入规模意外放大。
- [ ] 数据格式、公开接口和兼容性变化已覆盖相关读写方。
- [ ] 每条结论有文件位置、触发步骤、影响和验证证据。

## 输出格式

```markdown
## 发现
- [严重] `path/to/file:line` — 问题标题
  - 触发：输入或操作步骤
  - 影响：可观察到的错误或风险
  - 证据：代码路径或测试结果
  - 建议：最小修复方向

## 验证
- 已运行：`命令` → 结果
- 未验证：范围与原因
```

没有确认的问题时明确写“未发现可确认问题”，并列出仍未覆盖的路径。

## 常见陷阱

- 只看 diff，不追踪调用者和配置入口。
- 将个人风格偏好当成缺陷，或没有复现路径就给高严重级别。
- 把测试存在、测试通过和真实环境可用混为一谈。
