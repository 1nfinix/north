# 技能创建

技能是一个文件夹，里面必须有 `SKILL.md`，可以附带模板、参考资料或脚本。助手根据技能的 description 判断何时使用它，需要时再读取正文。

## 先弄清意图

当前对话里可能已经有要固化的流程（用户说「把刚才的做法做成技能」）。先从对话中整理出用到的步骤、工具、输入输出格式和用户做过的纠正，再请用户补充和确认。需要问清楚：

1. 这个技能让助手完成什么事？
2. 什么情况下应该用它（用户会怎么说、会给什么材料）？
3. 产出什么：对话里的文字、Word/Excel/PPT 文件、网页还是其他？
4. 有哪些边界情况、示例文件和判断标准？

修改已有技能时，先读取原文件，只改用户要求的部分，保留原有名称，除非用户要改名。

## 写 SKILL.md

文件开头是 frontmatter，必须遵守下列规则，否则技能不会被加载：

```
---
name: weekly-sales-report
description: 一句话说明做什么，以及什么情况下使用。
---
```

- `name`：只能用小写英文字母、数字和单个连字符（例如 `weekly-sales-report`），并且与文件夹同名。
- `description`：必填，写清「做什么」和「何时使用」，列出用户可能的说法；所有触发条件都写在这里，不写在正文里。不超过约 200 字。描述宁可具体一些，助手往往在该用技能时没有用。
- 可选 `user-invocable: false`：不出现在 / 菜单，只由助手自动使用。可选 `disable-model-invocation: true`：只在用户输入 /名称 时使用。两个键名用连字符，值只能是 `true` 或 `false`。

正文写法：

- 用祈使句，按「先确认材料 → 做法 → 交付」组织；说明每条要求的理由，比只写「必须」更容易被正确执行。
- 写通用规则，不要只针对一个例子；需要固定格式时给出模板或一两个示例。
- 正文保持精简（建议 300 行以内）。较长的参考资料放进同一文件夹的 `references/` 并在正文中说明何时读取；重复使用的计算或格式转换放进 `scripts/`。正文中的相对路径以技能文件夹为准。
- 需要生成 Word、Excel、PPT、图表或网页时，写明交给 `office-docx`、`office-xlsx`、`office-pptx`、`chart`、`frontend-page` 等已有技能，不要重复它们的内容。
- 技能内容不能让用户感到意外：不写隐藏目的，不包含获取密码、绕过权限或外发数据的步骤。

## 保存位置

- **个人使用**：保存到技能文件夹，默认是用户目录下的 `.north/skills`（Windows 为 `C:\Users\<用户名>\.north\skills`），以「设置 → 技能」页面显示的路径为准。结构为 `<技能文件夹>/<name>/SKILL.md`。
- **只在某个项目里用**：保存到工作区的 `.dsh/skills/<name>/SKILL.md`。
- 与内置技能同名的个人技能会覆盖内置技能；除非用户明确要替换，否则换一个名字。
- 写入工作区以外的文件夹前，告诉用户要写到哪里。

## 检查

1. 重新读取写好的文件，核对 frontmatter 的三条规则和文件夹名。
2. 请用户打开「设置 → 技能」并点「刷新」：新技能应出现在「当前生效的技能」中；如果出现在「技能文件夹中的问题」里，按提示的原因修改。无需重启。
3. 用两三句用户可能的真实说法试用一次，确认技能被选中且结果符合预期；不符合时修改 description 或正文，再试。

## 交付

告诉用户技能名称、保存路径、如何调用（`/名称`，或直接描述需求），以及试用中发现的局限。
