# 单元测试

## 何时使用

新增或修改可隔离的函数、服务或配置解析行为，需要用快速、确定性的测试锁定输入输出时使用。若行为依赖真实进程、浏览器或远端服务，说明单元测试的覆盖边界并选择现有集成测试。

## 分步流程

1. 阅读被测代码、现有相邻测试、仓库测试命令和夹具约定，先列出行为表：正常、边界、错误、取消或重复调用。
2. 在 PowerShell 和 Git Bash 中可用以下命令定位测试和脚本；把名称换成实际符号：

   ```text
   git grep -n 'functionName'
   git grep -n 'test:' -- package.json
   git status --short
   ```

3. 写能观察外部行为的断言：返回值、状态变化、事件或错误类型。测试名描述条件和结果，避免复述实现步骤。
4. 对文件、时间、随机数、网络等不稳定依赖使用项目已有注入点或夹具；每个测试清理临时目录、mock 和监听器。
5. 用项目现有的测试入口运行单个文件。例如项目使用 Vitest 时，两种 shell 均可执行 `pnpm exec vitest run path/to/file.spec.ts`；其他项目改用其既有脚本。
6. 确认新增测试在错误实现下会失败，再运行相关测试和适用的类型或 lint 检查。只因具体风险扩大到更大测试范围。

## 检查清单

- [ ] 测试验证公开行为而非私有调用顺序。
- [ ] 正常输入和至少一个实际边界输入均覆盖。
- [ ] 失败路径检查错误类型或可操作信息。
- [ ] 时间、随机值和网络依赖可控。
- [ ] 临时资源和 mock 在成功、失败时都清理。
- [ ] 测试之间不共享可变状态或依赖执行顺序。
- [ ] 测试命令和退出码已记录，未将跳过视为通过。
- [ ] 断言能检测目标回归，不仅重复实现中的常量。

## 输出格式

```markdown
## 行为覆盖
| 条件 | 预期 | 测试文件 |
|---|---|---|
| 示例输入 | 可观察结果 | `path/to/file.spec.ts` |

## 验证
- `命令` → 通过数或失败摘要
- 未覆盖：原因与所需测试层级
```

## 常见陷阱

- 为达到覆盖率数字写不能发现错误的断言。
- 在单元测试里访问真实服务，造成环境依赖和不稳定失败。
- 只测试成功路径，遗漏空值、重复调用或清理失败。
